# Plex HDHomeRun Bridge For octopus NET Pro Design

## Summary

Build a headless Nuxt 4 service that runs on the same LAN as Plex and an octopus NET Pro DVR. The service emulates a single HDHomeRun receiver so Plex can discover it as a tuner device, while the exposed channel lineup is sourced from a configured M3U playlist generated by octopus. The bridge does not transcode, remux, or otherwise transform streams. It preserves the original stream URLs, including descrambler query parameters already embedded in the playlist, so Plex can play channels that are otherwise not supported through native octopus discovery.

## Goals

- Emulate one HDHomeRun-compatible device discoverable by Plex on the local network
- Load channel definitions from a configurable M3U URL
- Expose a Plex-compatible channel lineup derived from that playlist
- Serve channel URLs as true pass-through targets without ffmpeg or stream conversion
- Run cleanly as a headless Docker-friendly service configured entirely through environment variables

## Non-Goals

- XMLTV or EPG support in v1
- User-facing configuration UI
- Stream transcoding, restreaming for format conversion, or buffering pipelines
- Multi-device HDHomeRun emulation
- Long-term persistence beyond in-memory lineup state and env-based config

## Runtime Model

The service is a single Nuxt 4 application using Nitro for the server runtime. It runs as one container on the same LAN as Plex. Configuration is provided exclusively through environment variables, including the M3U source URL, advertised device identity, advertised base URL overrides when needed, tuner count, and playlist refresh interval.

At startup, the service validates configuration, fetches the M3U playlist, parses channels into an in-memory normalized model, and starts both HTTP handling and HDHomeRun discovery handling. If the initial playlist fetch fails, the service exits with an error so container restart behavior surfaces the issue immediately.

## High-Level Architecture

### 1. Configuration Layer

This layer reads environment variables and validates them into a typed runtime config object. Important values include:

- `M3U_URL`
- `HDHR_TUNER_COUNT` with default `4`
- `PLAYLIST_REFRESH_SECONDS` with default `300`
- `HDHR_FRIENDLY_NAME`
- `HDHR_DEVICE_ID` or a stable deterministic fallback
- `SERVER_PORT`
- optional advertised host or base URL overrides for environments where direct host inference is unreliable

Invalid config should fail fast during startup with actionable log output.

### 2. Playlist Loader And Parser

This layer fetches the M3U file and converts entries into a normalized channel model. Each channel record should include:

- stable internal channel ID
- display name
- channel number if present
- logo URL if present
- group title if present
- original stream URL exactly as provided by the playlist

The parser must preserve stream URLs and query strings without modification. Channels missing a usable stream URL are excluded from the exposed lineup with a log entry describing why.

### 3. HDHomeRun Emulation Layer

This layer exposes the minimal protocol surface Plex needs for live TV integration:

- LAN discovery response for an HDHomeRun-like device
- HTTP metadata endpoints such as `/discover.json`
- XML device description endpoint such as `/device.xml`
- lineup endpoint such as `/lineup.json`

The bridge presents itself as one virtual HDHomeRun device with a configurable tuner count. Device identity must remain stable across restarts so Plex does not treat it as a new tuner after each deploy.

### 4. Channel Serving Layer

This layer exposes per-channel URLs that Plex can use for playback. The first implementation mode should be HTTP redirect pass-through. Each lineup entry points to a bridge-owned channel URL, and that URL responds with a redirect to the original octopus stream URL.

This preserves a true no-conversion path while keeping the bridge free to own stable outward-facing lineup URLs. If later testing shows certain Plex flows require reverse proxying instead of redirecting, that should be added as a separate optional mode rather than built into v1.

## Protocol And Compatibility Strategy

The service should follow the HDHomeRun advertisement and endpoint shape used by existing bridge implementations closely enough for Plex interoperability, while intentionally implementing only the subset required for discovery and playback. The project should use xTeVe and related HDHomeRun protocol references as interoperability guides, not as an architecture template. The explicit requirement is to avoid the ffmpeg-driven behavior that makes xTeVe brittle for this use case.

Compatibility priority for v1:

1. Plex can discover the device on the LAN
2. Plex can fetch device metadata and lineup data successfully
3. Plex can start playback for channels whose URLs already work directly from the M3U source

Anything beyond this core path should be deferred until interoperability testing proves it is needed.

## Data Model

The normalized in-memory channel structure should be intentionally small:

- `id`
- `name`
- `number`
- `logoUrl`
- `groupTitle`
- `streamUrl`
- `sourceHash` or equivalent stable derivation used for identity consistency

The lineup response adapter maps this internal model into whatever exact fields Plex expects from an HDHomeRun lineup entry.

## Refresh Behavior

The service refreshes the M3U playlist periodically, default every 300 seconds. Refreshes should be atomic:

- fetch and parse into a candidate lineup
- validate candidate entries
- replace the active in-memory lineup only if parsing succeeds

If a periodic refresh fails, the service logs the error and continues serving the last good lineup. This prevents temporary upstream failures from breaking Plex immediately.

## Networking Behavior

The service is designed for same-LAN deployment. Discovery replies should advertise the HTTP endpoint base URL that Plex can reach directly from the local network. Because containers can make host detection ambiguous, config should allow explicit override of the advertised host or base URL for reliable deployment in Docker.

The bridge should not assume NAT traversal or internet exposure. Security hardening for hostile networks is out of scope for v1, though the service should avoid obviously unsafe behavior such as exposing sensitive config values in public endpoints.

## Error Handling

### Startup Errors

- missing or invalid `M3U_URL`: fail startup
- initial fetch failure: fail startup
- zero valid channels after parsing: fail startup
- invalid advertised host configuration: fail startup

### Runtime Errors

- periodic refresh failure: log and keep last known good lineup
- malformed channel entry: exclude channel and log reason
- request for unknown channel ID: return `404`
- downstream octopus URL temporarily unavailable: allow the client to experience the upstream error naturally through redirect behavior

## Logging And Observability

Logging should be structured enough to support container usage:

- startup config summary with sensitive values omitted
- playlist fetch success and failure
- channel counts after parsing
- periodic refresh success and failure
- discovery requests received
- lineup requests received
- channel requests received with channel ID and channel name where available

Verbose request logging can be gated behind a debug env flag if needed, but basic operational logs should exist by default.

## Testing Strategy

### Unit Tests

- config parsing and validation
- M3U parsing for representative channel entries
- stable channel ID derivation
- stable device ID selection logic
- lineup serialization
- device metadata serialization

### Integration Tests

- startup with a mocked M3U source succeeds
- startup with invalid config fails
- periodic refresh swaps in a new lineup only after successful parsing
- `/discover.json` returns expected HDHomeRun-style metadata
- `/device.xml` returns valid device description
- `/lineup.json` returns channel entries with bridge-owned playback URLs
- channel playback URL returns redirect to the original octopus stream URL unchanged

### Manual Verification

- run container on same LAN as Plex
- confirm Plex discovers the tuner
- confirm Plex loads the lineup
- confirm playback works for descrambled channels sourced from octopus-generated M3U URLs

## Open Decisions Deferred Beyond V1

- XMLTV or guide integration
- optional reverse-proxy playback mode
- richer health endpoints and metrics
- channel grouping or filtering controls
- persistence of cached lineup between restarts

## Recommended Initial File Boundaries

To keep the code easy to reason about, the implementation should start with focused server-side modules:

- runtime config module
- M3U fetch and parse module
- channel model and serializers
- HDHomeRun discovery responder
- HTTP handlers for device and lineup endpoints
- HTTP handler for channel redirect endpoint

Nuxt should be used as the application shell, but the core bridge logic should remain framework-light so protocol and parsing behavior are easy to test directly.

## Acceptance Criteria

- The service runs as a single Nuxt 4 container with env-only configuration
- Plex can discover the service as one HDHomeRun-style device on the LAN
- Plex can fetch lineup data derived from the configured M3U playlist
- Playback URLs preserve octopus query parameters and avoid transcoding
- Playlist changes are picked up automatically on the configured refresh interval
- The service continues serving the last known good lineup if later refreshes fail
